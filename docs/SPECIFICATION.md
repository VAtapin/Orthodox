# Техническое задание: WordPress-плагин «Приход»

## 1. Цель

Разработать самостоятельный WordPress-плагин **«Приход»** для православных храмов, приходов и монастырей.

Плагин должен предоставлять основные функции самостоятельно и работать с любой совместимой темой WordPress.

Дополнительная тема «Приход» и расширения подключаются отдельно.

Главный принцип:

**один основной плагин → основные функции прихода → дополнительные возможности через независимые расширения.**

---

# 2. Основные функции «Прихода»

В основной плагин входят:

- профиль прихода;
- один или несколько храмов / мест служения;
- контакты;
- духовенство;
- расписание богослужений;
- ближайшее богослужение;
- объявления и стандартные записи WordPress;
- обращения к священнику;
- мастер первоначальной настройки;
- управление структурой сайта;
- Gutenberg-блоки;
- права доступа;
- диагностика состояния сайта;
- механизм интеграции с дополнительными плагинами.

Расписание и обращения должны быть внутренними отключаемыми модулями.

Отключение модуля не удаляет его данные.

---

# 3. Профиль прихода

Хранить:

- тип: храм / приход / монастырь / часовня;
- полное и краткое название;
- описание;
- адрес;
- телефон;
- email;
- сайт;
- часовой пояс;
- основной язык;
- духовенство;
- одно или несколько мест служения.

Каждое место служения может иметь:

- название;
- адрес;
- контакты;
- описание;
- собственное расписание.

---

# 4. Расписание богослужений

Это центральный модуль.

Поддержать:

- регулярные службы;
- разовые службы;
- праздничные службы;
- повторение по дням недели;
- дату и время;
- место служения;
- описание;
- время окончания;
- отмену отдельной службы;
- перенос;
- изменение времени;
- исключения из регулярного расписания.

Православный календарь не создаёт расписание автоматически.

Фактическое расписание всегда задаётся приходом.

## Вывод расписания

Поддержать:

- ближайшее богослужение;
- список ближайших служб;
- неделю;
- месяц;
- фильтр по месту служения;
- печатную версию.

Учитывать timezone сайта/прихода и переход летнего/зимнего времени.

---

# 5. Обращения к священнику

Публичный посетитель может отправить обращение без регистрации.

Минимальные данные:

- имя;
- email;
- тема;
- текст обращения.

Административная часть внутри WordPress:

- список обращений;
- просмотр обращения;
- статусы;
- назначение ответственного;
- внутренние заметки;
- ответ пользователю по email;
- закрытие;
- удаление.

Статусы минимум:

- новое;
- в работе;
- ожидает ответа;
- отвечено;
- закрыто.

Доступ к обращениям должен регулироваться отдельными capabilities.

Обычный редактор WordPress не должен автоматически получать доступ к обращениям.

Архитектурно предусмотреть:

- вложения;
- историю переписки;
- дополнительные каналы связи;
- сроки хранения;
- экспорт и удаление персональных данных.

---

# 6. Новости, объявления и проповеди

Не создавать отдельную систему публикаций без необходимости.

Использовать стандартные WordPress Posts, категории и таксономии.

Мастер может подготовить:

- категорию «Новости»;
- категорию «Объявления»;
- категорию «Проповеди»;
- Gutenberg patterns для публикаций.

Плагин может добавлять дополнительные блоки и метаданные, но стандартный редактор WordPress должен сохраняться.

---

# 7. Gutenberg-блоки

Минимальный набор:

- сведения о приходе;
- контакты;
- духовенство;
- расписание;
- ближайшее богослужение;
- список ближайших служб;
- форма «Вопрос священнику».

Блоки принадлежат плагину.

Тема отвечает только за оформление.

Предусмотреть шорткоды как дополнительный вариант размещения там, где блоки использовать неудобно.

---

# 8. Мастер первоначальной настройки

После активации плагина показать закрываемое приглашение начать настройку.

Не выполнять автоматический redirect.

Мастер должен сначала проанализировать существующий сайт.

Проверить:

- активную тему;
- страницы;
- главную страницу;
- меню/navigation;
- язык;
- timezone;
- установленные плагины;
- существующий контент;
- наличие уже созданных страниц «Прихода».

## Сценарий интервью

Вопросы показываются последовательно и зависят от предыдущих ответов.

Основные этапы:

1. Тип организации.
2. Один храм или несколько мест служения.
3. Основные сведения.
4. Контакты.
5. Языки.
6. Духовенство.
7. Расписание.
8. Обращения к священнику.
9. Новости / объявления / проповеди.
10. Дополнительные плагины.
11. Выбор темы.
12. План изменений.
13. Подтверждение.
14. Выполнение.
15. Проверка результата.
16. Предварительный просмотр страниц.
17. Публикация.

У каждого вопроса должна быть возможность:

**«Настроить позже».**

Если функция не выбрана, связанные вопросы не показывать.

---

# 9. Безопасное изменение сайта

До финального подтверждения мастер не должен:

- создавать страницы;
- менять существующие страницы;
- менять главную;
- изменять меню/navigation;
- активировать тему;
- устанавливать дополнительные плагины.

Перед применением показать полный план.

Например:

- какие страницы будут созданы;
- какие существующие страницы будут использованы;
- какие блоки будут добавлены;
- какие пункты меню появятся;
- какие плагины будут предложены;
- какая тема будет использоваться;
- какие внешние сервисы подключаются.

Новые страницы первоначально создавать как `draft`.

Публикация выполняется отдельно.

---

# 10. Повторный запуск мастера

Мастер должен безопасно запускаться сколько угодно раз.

Он должен:

- помнить созданные ресурсы по WordPress ID;
- находить существующие страницы;
- не создавать дубликаты;
- учитывать ручные изменения;
- не перезаписывать контент без подтверждения;
- продолжать незавершённую настройку;
- позволять подключать новые функции позднее.

Если пользователь изменил созданную мастером страницу, мастер должен сохранить эти изменения.

---

# 11. Структура сайта

Мастер может предложить следующие страницы:

- Главная;
- О приходе;
- Духовенство;
- Расписание богослужений;
- Вопрос священнику;
- Первый раз в храме;
- Новости;
- Проповеди;
- Контакты.

Не все страницы обязательны.

Если аналогичная страница уже существует, предложить использовать её.

---

# 12. Тема «Приход»

Тема не обязательна.

Основные функции плагина должны работать с другими WordPress-темами.

Если пользователь хочет тему «Приход»:

- показать её;
- предложить установить;
- дать предварительный просмотр;
- отдельно предложить активировать.

Установка и активация темы — разные действия.

Тема отвечает за:

- оформление;
- шаблоны;
- стили;
- patterns;
- визуальную интеграцию блоков «Прихода».

Данные и функциональность в теме не хранить.

---

# 13. Дополнительные плагины

## Православный календарь

Существующий самостоятельный плагин.

При подключении к «Приходу» можно использовать:

- календарь;
- праздник дня;
- святых;
- чтения;
- другие доступные данные.

Перед интеграцией проверить фактический код плагина и его существующие API/блоки.

Не предполагать функции, которых нет.

---

## «Записки»

Существующий самостоятельный плагин.

Он продолжает работать независимо.

Интеграция с «Приходом» может добавлять его страницы и блоки в общую структуру сайта.

Сам плагин «Записки» позднее расширяется:

- существующие записки;
- пожертвования вместе с записками;
- самостоятельные пожертвования;
- целевые сборы;
- регулярная поддержка.

Эти функции не включать в основной плагин «Приход».

---

# 14. Внешние интеграции

Архитектурно предусмотреть отдельные расширения:

- Telegram;
- WhatsApp;
- Facebook;
- другие социальные сети и сервисы.

Для одного сервиса должно быть одно общее подключение.

Например, Telegram-интеграцию должны использовать:

- уведомления об обращениях;
- новости;
- объявления;
- изменения расписания.

Не создавать несколько независимых Telegram-подключений для разных модулей.

---

# 15. Интеграционный механизм

REST namespace:

`prihod/v1`

использовать для REST API самого продукта.

Для связи WordPress-плагинов использовать PHP:

- actions;
- filters;
- interfaces;
- registry/services.

Дополнительный плагин должен иметь возможность сообщить «Приходу»:

- ID;
- название;
- возможности;
- настройки;
- блоки;
- страницы;
- внешние сервисы;
- состояние подключения;
- health check.

Не строить чрезмерно сложный framework заранее.

Сделать небольшой расширяемый контракт и развивать его по мере появления реальных интеграций.

---

# 16. Административный интерфейс

Основное меню:

`Приход`

Разделы:

- Обзор;
- Сведения о приходе;
- Места служения;
- Духовенство;
- Расписание;
- Обращения;
- Структура сайта;
- Возможности;
- Подключения;
- Проверка сайта;
- Мастер настройки;
- Настройки.

На Overview показывать основные состояния и проблемы.

Например:

- расписание работает;
- следующая служба определена;
- страница расписания опубликована;
- есть новые обращения;
- email настроен;
- календарь подключён;
- «Записки» не подключены;
- Telegram требует настройки.

---

# 17. Роли и права

Использовать WordPress capabilities.

Минимально предусмотреть отдельные права для:

- управления приходом;
- управления расписанием;
- просмотра обращений;
- ответа на обращения;
- управления настройками и интеграциями.

Не привязывать всё только к `administrator`.

---

# 18. Данные

Отключение модуля не удаляет данные.

Деактивация плагина не удаляет данные.

Обычное удаление плагина также не должно без предупреждения уничтожать пользовательский контент.

Для полного удаления предусмотреть отдельное явно подтверждаемое действие.

---

# 19. WordPress.org

Разработка должна соответствовать требованиям WordPress.org.

В частности:

- никаких скрытых установок;
- никаких автоматических установок дополнительных компонентов без согласия;
- никаких скрытых активаций;
- никаких изменений существующего сайта без подтверждения;
- никакой загрузки исполняемого кода с внешнего сервера;
- корректные capabilities, nonce, sanitization и escaping;
- переводимость всех строк;
- нормальная работа без темы «Приход»;
- дополнительные плагины должны быть самостоятельными.

Если дополнительный компонент ещё отсутствует в WordPress.org, мастер может показать инструкцию по ручной установке, но не загружать его автоматически с нашего сервера.

---

Проектировать сразу под полный функционал, но реализовывать последовательно.

- структура плагина;
- профиль прихода;
- места служения;
- духовенство;

- административный интерфейс;
- база интеграционного механизма.

## Этап 2 — Расписание

- модель расписания;
- регулярные и разовые службы;
- исключения;
- несколько мест;
- ближайшая служба;
- Gutenberg-блоки;
- печатный вывод.

## Этап 3 — Обращения

- православный календарь;
- «Записки»;
- Telegram;

# 21. Главное требование к разработке

Не делать отдельные временные реализации, которые потом придётся выбрасывать при переходе к следующему этапу.

Архитектуру сразу строить для полного продукта.

При этом не усложнять код абстракциями, которые пока не нужны.

Каждый этап должен завершаться рабочим и тестируемым состоянием проекта.

Перед началом интеграции существующих плагинов обязательно сначала изучить их фактический код.
