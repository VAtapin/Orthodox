# Архитектура «Прихода»

## Границы

Плагин владеет данными и функциями, тема — оформлением. Календарь, «Записки» и
интеграции остаются самостоятельными компонентами. Необходимый конечный объём
сохранён в SPECIFICATION.md; реализация текущего этапа не подменяет полный продукт.
При различии последовательности двух исходных документов этапы берутся из
раздела 20 ТЗ: Core → расписание → обращения → мастер → тема → интеграции.

Нет временных страниц расписания, фиктивных обращений и имитаций подключения API.
REST namespace `prihod/v1` зарезервирован; маршруты пока не регистрируются.

## Core: существующие данные

| Сущность | Хранение | Содержание |
| --- | --- | --- |
| Профиль | option `prihod_profile` | Тип, названия, описание, адрес, контакты, timezone, язык |
| Место служения | CPT `prihod_location` | Название, описание, статус, revisions |
| Сведения о месте | meta `_prihod_details` | Адрес, контакты, timezone |
| Священнослужитель | CPT `prihod_clergy` | Имя, описание, статус, revisions |
| Сведения о духовенстве | meta `_prihod_details` | Сан, контакты, массив `location_ids` |
| Версия выдачи прав | option `prihod_capabilities_version` | Идемпотентная начальная выдача capabilities |

Стабильные WordPress ID мест служения будут внешними ключами расписания.
Профиль читается через `Profile::get()`, сведения записей — `Directory::details()`.
Данные метаполей пока не имеют истории revisions; история самого названия и
описания поддерживается WordPress. Записи директории не имеют публичных архивов,
публичного REST или permalink: будущие блоки должны явно выводить только
предназначенные для публикации поля опубликованных записей.

Часовой пояс профиля независим от WordPress. При отсутствии именованного timezone
сайта начальное значение — UTC; его следует выбрать вручную. Собственный пояс места
не обязателен. Это позволяет расписанию учитывать DST без фиксированных offsets.

Сохранение профиля использует Settings API с capability `manage_prihod`.
Сохранение директории проверяет capability, объектное право, nonce и autosave/revision.
Некорректные поля не затирают прежние значения; неизвестные входные ключи игнорируются.
Ссылки на другие типы записей и удалённые места отклоняются.

## Последующие модели (план, не реализация)

- Расписание: отдельные сущности правил повторения, разовых событий и исключений.
  Исключение адресуется ID правила и исходной локальной датой occurrence; перенос
  не создаёт второе независимое регулярное правило. Хранить локальное время и
  IANA timezone, вычислять UTC для конкретного occurrence. Окончательная схема и
  DST-политика для неоднозначного/несуществующего времени — часть этапа 2.
- Обращения: закрытое хранилище обращения, сообщений и назначений. Оно не использует
  публичные записи духовенства; capability проверки нужны на каждой операции.
  Отправитель без обязательного WordPress user ID. Канал email отделён от истории
  сообщений, чтобы позже добавить кабинет и другие каналы. Retention, privacy
  export/erase и ограничения формы входят в этап обращений.
- Мастер: отдельное состояние интервью и реестр WordPress ID созданных ресурсов;
  анализ → план → подтверждение → применение → отдельная публикация.
  При изменении ресурсов после preview план должен быть перепроверен. Ручной контент
  сохраняется, повторный запуск не дублирует ресурсы. До подтверждения — только
  состояние интервью, без изменений страниц/меню/темы.
- Модули: отключение убирает обработчики и интерфейс, но сохраняет данные. Переключатели
  будут добавляться вместе с работающими модулями, а не включать отсутствующий код.

## Контракт расширений

PHP interface `Prihod\Integration`: `id(): string`, `describe(): array`,
`health(): array`. Регистрация на action `prihod_register_integrations`
в `init`, priority 20. Подключающий плагин подписывается заранее, например на
`plugins_loaded`; при отсутствии «Прихода» этот action не вызывается.
Свои основные функции расширение запускает независимо от этого action.

`describe()` описывает `name`, `capabilities`, `settings_url`, `blocks`, `pages`,
`external_services`; последние поля пока информационные. Их наличие не даёт
«Приходу» права устанавливать плагины или изменять сайт. `health()` возвращает
`status` (`ready`, `needs_setup`, `unavailable`) и переводимый `message`.
Проверка должна использовать локальный кэш, а не выполнять сетевые запросы при
открытии административной страницы. Секреты не включаются в описание и отчёты.

ID: `[a-z][a-z0-9_-]{0,63}`, уникальный. Некорректный/повторный ID отклоняется
исключением; адаптер отвечает за корректную регистрацию. Ошибка `describe/health`
изолируется в отчёте и не выводит текст исключения в UI.

Для внешнего сервиса — одно подключение, используемое разными событиями модулей.
Фактические адаптеры календаря и «Записок» проектируются только после чтения их кода.

## Жизненный цикл

Активация выдаёт начальные права. Не меняет фронтенд и чужие настройки.
Деактивация сохраняет данные. `uninstall.php` намеренно ничего не удаляет.
Права также сохраняются, чтобы не терять назначенные полномочия при переустановке.
Полное удаление данных — будущая отдельная подтверждаемая операция.
