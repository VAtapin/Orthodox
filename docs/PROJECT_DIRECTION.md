Концепцию не сокращаем. Нужно делать полноценный продукт **«Приход»**, но реализовывать его по этапам, чтобы каждый этап оставлял рабочее состояние проекта.

## 1. Объём проекта

Не нужно ограничивать первую архитектуру только расписанием.

Сразу проектируем конечную систему:

- профиль прихода;
- один или несколько храмов / мест служения;
- расписание;
- ближайшее богослужение;
- исключения, переносы и отмены;
- обращения к священнику;
- права доступа;
- мастер первоначальной настройки;
- Gutenberg-блоки;
- структура страниц;
- интеграции с календарём и «Записками»;
- расширяемый механизм внешних интеграций.

Реализация идёт по этапам, но архитектуру сразу строим под полный объём.

## 2. Этапы разработки

### Этап 1
Основа плагина:

- профиль прихода;
- места служения;
- модель данных;
- capabilities;
- административная структура;
- мастер настройки;
- базовые Gutenberg-блоки.

### Этап 2
Полное расписание:

- регулярные службы;
- разовые службы;
- праздничные службы;
- отмены;
- переносы;
- изменение времени;
- несколько мест служения;
- часовые пояса;
- ближайшее богослужение;
- неделя / месяц;
- печать.

### Этап 3
Обращения:

- публичная форма;
- закрытый раздел WordPress для ответственных;
- статусы;
- назначение ответственного;
- переписка;
- email-ответы;
- права доступа;
- сроки хранения;
- удаление данных;
- защита персональных данных.

Регистрация посетителя не должна быть обязательной.

Для первого варианта достаточно формы и ответа по email, но архитектура должна позволять позднее добавить личный кабинет посетителя.

### Этап 4
Мастер и автоматическая подготовка сайта:

- анализ существующего сайта;
- создание страниц;
- Gutenberg-композиции;
- работа с главной;
- меню/navigation;
- повторный запуск без дублей;
- preview плана изменений;
- подтверждение перед изменениями;
- диагностика результата.

### Этап 5
Интеграции:

- Православный календарь;
- «Записки»;
- Telegram;
- WhatsApp;
- социальные сети;
- другие будущие модули.

## 3. Расписание

Согласен, это центральная модель.

Нужно сразу предусмотреть:

- регулярные службы;
- разовые события;
- исключения;
- отмены;
- переносы;
- изменение времени;
- места служения;
- timezone.

Православный календарь может давать информацию о праздниках и днях, но **никогда не создаёт фактическое расписание автоматически**.

Фактические богослужения определяет приход.

## 4. Обращения

Под «закрытым кабинетом» сейчас понимается административный раздел внутри WordPress.

Публичный пользователь:

- не обязан регистрироваться;
- отправляет вопрос через форму;
- получает ответ по email.

Ответственные сотрудники:

- видят обращения только при наличии отдельного capability;
- могут менять статус;
- назначать ответственного;
- отвечать;
- закрывать обращение;
- удалять данные.

Вложения можно предусмотреть архитектурно и добавить после базовой переписки.

## 5. REST API и внутренние интеграции

Согласен, это разные вещи.

Использовать:

`prihod/v1`

только как namespace REST API.

Для интеграций между установленными плагинами использовать PHP:

- actions;
- filters;
- interfaces / registry;
- service contracts.

Не нужно заранее строить слишком сложную абстрактную систему. Создать простой расширяемый контракт и развивать его по мере появления реальных интеграций.

## 6. Повторный запуск мастера

Обязательно.

Мастер должен:

- знать созданные им страницы по ID;
- обнаруживать существующие страницы;
- не создавать дубликаты;
- не перезаписывать пользовательские изменения;
- не менять главную страницу без подтверждения;
- не менять navigation/menu без подтверждения;
- уметь продолжать незавершённую настройку;
- уметь добавлять новые возможности позже.

Отключение внутреннего модуля не удаляет данные.

Удаление плагина также не должно автоматически уничтожать пользовательские данные.

Полное удаление данных — только отдельным явно подтверждённым действием.

## 7. Telegram

Согласен: не нужно делать отдельные независимые подключения Telegram для каждого сценария.

Должна быть одна общая интеграция Telegram, которую смогут использовать разные функции:

- уведомления о новых обращениях;
- публикация новостей;
- публикация объявлений;
- уведомления об изменениях расписания.

То же относится к другим внешним сервисам.

## 8. Календарь и «Записки»

Перед реализацией интеграции обязательно проверить фактический код существующих плагинов.

Не предполагать наличие API или блоков, которых там нет.

Оба плагина остаются самостоятельными и могут работать без «Прихода».

«Приход» только интегрирует их в общий интерфейс и мастер.

Плагин **«Записки»** в дальнейшем расширяем:

- существующие записки;
- пожертвования вместе с записками;
- отдельные пожертвования;
- целевые сборы;
- регулярная поддержка.

Это развитие самого плагина «Записки», а не функциональность основного плагина «Приход».

## Главное

Не строить маленький MVP, который потом придётся переделывать.

Нужно сразу заложить архитектуру полноценной системы и реализовывать её последовательно:

**основа → расписание → обращения → мастер → интеграции → дополнительные возможности.**

Каждый этап должен завершаться рабочим состоянием проекта, но конечный объём функций из архитектуры не убираем.
