# Приход

Самостоятельный WordPress-плагин для православных храмов, приходов и монастырей.
Полный объём продукта зафиксирован в [ТЗ](docs/SPECIFICATION.md) и
[направлении проекта](docs/PROJECT_DIRECTION.md). Реализация выполняется по этапам
без сокращения конечных требований.

## Текущее состояние: 0.1.0, этап Core

Реализованы профиль прихода, места служения, духовенство, capabilities,
административное меню и PHP-контракт расширений. Один священнослужитель может быть
связан с несколькими местами служения. Каждое место может иметь собственный
именованный часовой пояс; пустое значение означает наследование часового пояса прихода.

Расписание, обращения, блоки/шорткоды, мастер, тема и реальные адаптеры внешних
плагинов пока не реализованы. Зарезервированные права этих модулей не означают,
что сами модули готовы. «Записки» и календарь не устанавливаются автоматически.

## Установка

Исходный каталог плагина — `prihod/`. Скопировать его целиком в
`wp-content/plugins/prihod/` существующего WordPress и активировать «Приход».
В админке появится меню «Приход». Первоначальное заполнение пока ручное.

Заявленный минимум: WordPress 6.5 и PHP 8.0. Production-окружение владельца:
Plesk и PHP 8.4. Отдельный Node build и Composer dependencies для плагина не нужны.
Проверка заявленного минимума должна дополняться интеграционными проверками WordPress.

Для установки через ZIP из PowerShell в корне репозитория:

```powershell
New-Item -ItemType Directory -Path build -Force | Out-Null
Compress-Archive -Path prihod -DestinationPath build/prihod-0.1.0.zip -Force
```

Активация не меняет тему, меню, главную страницу или язык/часовой пояс WordPress.
Обычное удаление и деактивация сохраняют данные и выданные права. Инструмент
полного подтверждаемого удаления данных ещё предстоит реализовать.
Сетевая активация: права инициализируются отдельно на каждом сайте при первой
загрузке активного плагина; данные хранятся в таблицах соответствующего сайта.

## Права

При первичной установке права получает администратор текущего сайта.
Проверки доступа используют capabilities, а не название роли. При обычной загрузке
плагин не восстанавливает отозванные права. При повторной активации начальные
права администратора выдаются заново.

| Capability | Назначение |
| --- | --- |
| `manage_prihod` | Профиль, места служения, духовенство |
| `manage_prihod_settings` | Настройки и подключения |
| `manage_prihod_schedule` | Будущее управление расписанием |
| `view_prihod_requests` | Будущий просмотр обращений |
| `reply_prihod_requests` | Будущие ответы |
| `assign_prihod_requests` | Будущее назначение ответственного |
| `delete_prihod_requests` | Будущее удаление обращений |

Назначение другим ролям выполняется существующими средствами управления
capabilities WordPress. Собственного редактора ролей пока нет.

## Проверки

```powershell
php tests/lint.php
php tests/run.php
```

Альтернатива при настроенном Composer: `composer check`. Установка зависимостей
не требуется. Unit-тесты используют изолированные подстановки функций WordPress;
они проверяют валидацию, сохранение данных, ограничения доступа и ошибки расширений.
Это не замена запуску плагина в WordPress. Интеграционный сценарий и его команда
описаны в `tests/README.md`.

## Production

Владелец устанавливает плагин самостоятельно. WordPress и production не изменяются
в рамках разработки. Устанавливаемым артефактом является только каталог `prihod/`
либо ZIP с этим каталогом, а не корень Git checkout.
Composer, npm, миграции и очистка кэшей для Core не требуются.
Серверная команда deployment не требуется: установка оставлена владельцу по его
явному указанию. Для будущих серверных операций применяется Plesk PHP 8.4.
